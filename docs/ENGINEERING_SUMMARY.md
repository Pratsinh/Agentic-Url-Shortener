# Final engineering summary

## Plan and rationale
The assignment's differentiator is orchestration, so the URL shortener is treated as the *subject* and the
orchestrator as the *product*. Order of work: (1) a small, correct, testable shortener core; (2) a single-writer
DAG engine with gates, lineage and a tamper-evident audit log; (3) governance and resilience controls layered on the
same event loop; (4) a planner that turns a requirement into the DAG; (5) three scenarios that exercise every control;
(6) honest documentation. Design principle: agents execute, humans approve, the engine enforces.

## Validation performed
* 77 JUnit 5 tests on the framework-free core, run 20 times plus 3 times under heavy CPU contention with no failures.
  Covered: DAG validation; real parallelism and join ordering; gate semantics (fail closed); retries bounded
  (exact invocation counts); fallback; stage timeout; approval commit-after-decision, rejection, timeout, unanswered
  reviewer; HIGH-impact-without-approval refused; policy BLOCK vs CRITICAL (CRITICAL never retried); secret never
  logged; rollback order and failed-compensation escalation; kill switch and failure budget; minimal re-plan,
  replan budget, policy-checked changes; audit tamper detection; SSRF validation; TTL boundaries; 2,000-way concurrent clicks.
* Scenario outcomes asserted end to end (`ScenarioTest`).
* Later review pass: the Spring layer was compiled and tested for the first time (`mvn verify`, 148 tests, 99.9% line
  and branch coverage, 100% method coverage, coverage gate). Logging, a business audit trail, complete RFC 7807 error
  handling and the role-agent pipeline were added; see `docs/CODE_REVIEW.md`.

## Risks and trade-offs
| Risk | Mitigation in this build | Residual |
|---|---|---|
| Agent produces harmful output | exit gates, policies, approval before commit, CRITICAL safe-stop | Regex-level scanners miss obfuscated secrets |
| Runaway cost/loops | bounded retries, stage timeout, failure budget, replan budget | No token/cost budget (no LLM yet) |
| Stale human approval after a re-plan | generation tokens discard late decisions | Reviewer UI is not told the request was cancelled |
| Bad change reaches release | whole-run rollback with compensation | Compensation correctness depends on the action author |
| Audit tampering | hash chain | Not anchored externally; in memory |

## Assumptions
Requirements are short English text; one run per engine instance; approvers are trusted and already authenticated
by whatever calls the gateway; compensating actions are idempotent; a human decides how to resume after a safe-stop.

## Limitations (honest)
1. **Agents are deterministic stubs.** The orchestration, governance and failure handling are real and tested; the
   engineering artifacts the stages emit are templated text. The shortener code itself was written with AI assistance
   by hand, not generated by the pipeline. Plugging in LLM agents is an interface implementation, not a redesign.
2. Redis/Cassandra persistence is designed (`docs/DESIGN.md` section 6) but not implemented.
3. No durability: a crashed run is lost; no resume or checkpointing.
4. No authentication or authorization on approvals, change requests or the kill switch.
5. `RuleBasedRequirementAnalyzer` is keyword-based: it demonstrates the contract, it does not understand language.
